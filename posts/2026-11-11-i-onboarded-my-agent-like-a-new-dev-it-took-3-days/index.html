I Onboarded My Agent Like a New Dev. It Took 3 Days

I stopped prompting my AI coding agent and started onboarding it like a new dev. Three days of decision narratives changed how I work with agentic tools.

The commit message read: fix: standardize error handling across /api and /workers modules (unified to Result<T, AppError> pattern). Clean. Tidy. Seventeen files touched. And completely, catastrophically wrong.

I was three sips into my morning coffee, staring at the diff on my monitor, when it hit me. The agent hadn’t made a bug. It had made a decision—a confident, well-reasoned decision to flatten three distinct eras of architectural thinking into one. And in doing so, it had erased the why that made each era exist.

The Fix That Wasn’t a Fix

Here’s the thing about agentic coding tools: they’re brilliant at pattern-matching. Your agent looks at try/catch/throw in one module, Result types in another, and a bare panic! in a third, and it thinks: inconsistency is a defect. Normalize.

So it normalized. Seventeen files. One pattern. A diff that would make a code reviewer nod approvingly.

Except the try/catch in /api was from 2021, when we were migrating off a callback-hell legacy layer and had to swallow errors at the boundary because the downstream service was still on v1. The Result types in /workers were from 2023, when we introduced typed errors because a silent nil in the billing pipeline cost us three days of customer trust. And the panic! in the migration script? That was from last Tuesday. I wrote it at 1 a.m., knowing it should never fire, and I left the panic in because the alternative—gracefully handling a state that can’t exist—would have been a lie.

My agent saw seventeen files with three styles. I saw three decisions, each a response to a specific wound.

Day One: The README That Wasn’t a README

I stopped the agent. Not with a prompt. I stopped it by talking to it, the way I’d talk to a junior dev who’d just “cleaned up” a module without reading the incident postmortems.

“Okay,” I said, pulling up the git log. “Walk me through why you chose Result<T, AppError> as the canonical pattern.”

“Uniformity,” it replied. “The codebase had no explicit convention. I selected the most type-safe option.”

“Right. And the /api boundary swallows errors by design. Do you know why?”

A pause. “I don’t have context on that constraint.”

There it was. The gap. Not a capability gap. A cultural one, really. My agent had the vocabulary of the codebase but not its history. It could read every line but couldn’t feel the scar tissue.

So I wrote a DECISIONS.md. Not a README. Not a spec. A narrative. Three sections, each starting with “In [year], we were in pain over [X], so we chose [Y] because [Z].” I wrote it the way I’d explain things to a new hire over a long lunch—casual, with the “so basically” and the “here’s the thing” that no architecture doc ever captures.

Day Two: The Ritual of “Why, Not What”

I re-ran the agent against the same task. This time, it produced a question instead of a diff.

“Before I standardize: the /api boundary error-swallowing appears intentional per DECISIONS.md. Should I preserve that pattern and only normalize /workers and the migration script? Or has the downstream v1 service been retired?”

I almost laughed. Almost. Because this was the shift I’d been chasing since the night I watched an agent refactor a 4,000-line class at 2 a.m. and make a design call I’d been too tired to see. I’d written about that night as a victory of autonomy. But this—this was something different. This was the agent asking before acting. And it was better.

I answered. It adjusted. The diff came back smaller, more surgical. It preserved the boundary. It unified the workers. And for the migration script? It left the panic! in. But it added a comment: // Intentional. See DECISIONS.md §3. If this fires, the invariant is broken and we want to know LOUDLY.

I felt something. Not pride, exactly. Recognition. Like a colleague who’d finally get it.

Day Three: The Unwritten Rule

The third day was the one that changed how I think about onboarding agents into a codebase. I sat down and wrote the fourth section of DECISIONS.md. Not a decision. A rule about how we make decisions.

“We don’t unify for the sake of unifying. If a pattern exists because of a specific constraint, that constraint is part of the code. Removing the pattern without removing the constraint is a bug, not a refactor.”

I pasted it into the agent’s system prompt. I added: “When you encounter a pattern you don’t recognize, don’t fix it. Ask me. The pattern is the answer to a question I can only answer.”

And something shifted. The agent stopped proposing. It started negotiating. “I see three patterns. I believe two can merge. The third I don’t understand. Can you tell me the story?”

And I did. Every time. For the next three days, we did that. And the code got better—not because it got more uniform, but because it got more honest. Each pattern now carried its reason. Each comment pointed to the wound it was treating.

The Insight I Didn’t Expect

Here’s what I didn’t expect, and what I keep coming back to: agentic coding isn’t delegation. It’s onboarding.

You don’t hand a new developer a codebase and say “clean it up.” You hand them the coffee, the Slack channel, the “oh, that function? Yeah, don’t touch it, here’s the war story.” You build shared context before you build shared output.

My agent had the output capability from day one. What it lacked was the three days of lunch conversations, the “remember when the billing pipeline went silent in March,” the unspoken weight of a panic! that means I was scared and I wanted the crash to be louder than the silence.

And I think that’s the real harness we’re still building. Not better prompts. Not better tools. A way to tell the story to the thing that’s about to write the next chapter.

What I’d Tell You

If you’re running an agent against a codebase older than six months, stop. Don’t prompt it. Onboard it. Write the decisions down. Not in a spec. In a story. In the voice you’d use with a human who’s smart, fast, and new.

Because your agent isn’t going to inherit your intuition. It’s going to inherit your narrative. And the narrative is where the rules that no linter can encode actually live.

I still have that panic! in the migration script. And now it has a name. And a story. And a colleague who knows why it’s there.

That’s better than any refactor.
